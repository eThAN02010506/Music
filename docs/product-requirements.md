## 1. 产品定位

Music Insight 是一位“可交互的音乐导赏老师”，也是一个本地优先、证据驱动的
音乐理解与演唱练习工具。

用户上传歌曲后，系统不只给出 BPM、调性、歌词、声音事件和情绪标签，还要帮助
普通听众理解：

- 音乐表达了怎样的气氛、情绪和意境；
- 这些感受由哪些具体声音形成；
- 每个段落在叙事或歌词中起什么作用；
- 歌词、旋律、和声、节奏、音色、力度、配器和空间感如何共同作用；
- 应该怎样复听，才能亲自听出这些变化。

核心原则是：

> 先帮助用户听懂整首音乐，再陪用户在每个具体时刻追问：
> “我为什么会产生这种感觉？”

### 1.1 目标用户

- 想听懂一首歌、但不熟悉乐理的普通听众；
- 希望练习听辨、理解编曲或积累音乐概念的学习者；
- 想把自己的演唱与参考歌曲做可重复比较的练习者；
- 需要查看任务进度、模型状态和失败原因的本地部署者。

### 1.2 用户要完成的任务

1. 上传一首歌，得到可信、可追溯、可复听的整体理解。
2. 播放到某个时刻时，马上询问“这里发生了什么，为什么我会有这种感觉？”
3. 框选或对比两个片段，听懂它们在声音与表达上的差异。
4. 修改不准确的歌词或重新聆听局部，而不是重跑整首歌曲。
5. 上传或录制自己的演唱，与原曲比较并保存个人练习记录。

## 2. 产品原则

1. **证据先于解释。** DSP、歌词和带时间的声音事件属于可观察证据；意境、
   段落作用和文化联想属于解释，界面和回答必须区分二者。
2. **先整体、再局部。** 先提供整首导赏和时间地图，再围绕播放位置持续问答。
3. **每个结论都可复听。** 重要解释必须关联可点击时间范围，并给出立即可做的
   复听任务。
4. **允许多种理解。** 不把音乐意境描述成唯一答案，不虚构作曲家、歌手或制作人
   的心理与创作意图。
5. **不确定就明确降级。** 模型或歌词证据不足时保守留空、降低置信度并说明原因，
   不能用流畅文字掩盖失败。
6. **避免重复计算。** 问答优先检索已有地图与附近证据；必要时只重听 15–30 秒，
   不在每次提问时重新分析整首歌曲。
7. **本地优先但不误导。** 账号、历史、播放器和 DSP 可留在本地；选择网络模型时，
   必须明确音频和相关上下文会发送到该服务。
8. **Provider 中立。** 能力由协议和探测结果决定，不根据模型名称或端口猜测。
9. **模块可替换。** 分析、Provider、教学、播放器、持久化、任务队列和评分保持
   清晰边界，错误降级和测试覆盖是功能的一部分。

## 4. 核心用户流程

### 4.1 上传并听懂歌曲

1. 用户登录，选择模型 Provider 或本地权重。
2. 用户上传音频，界面持续显示排队、预处理、DSP、模型和保存进度。
3. 即使模型失败，任务也返回可用的 DSP 证据和明确警告。
4. 任务完成后，系统从已有证据自动准备基础音乐理解地图。
5. 用户可以立即播放、点击时间节点复听和开始问答，也可以选择模型增强导赏。

### 4.2 边听边问

1. 用户播放歌曲、点击“解释当前 15 秒”或在波形上选择范围。
2. 系统自动带上歌曲、时间、段落、附近歌词、附近证据、歌曲级对话和听觉水平。
3. 服务端检索附近地图事件；只有证据不足且 Provider 支持时才局部重听。
4. 回答先直接回应问题，再展示听觉证据、表达作用、复听任务和其他可能理解。
5. 用户点击回答中的时间或播放器动作，立即跳转、播放或循环相应片段。

### 4.3 比较两个片段

1. 用户设置 A/B 范围；没有手动设置时，界面可创建相邻默认范围。
2. 用户先连续播放 A→B，再提交比较问题。
3. 回答分别引用两个范围，说明可观察差异、表达影响和具体听辨任务。

### 4.4 演唱练习

1. 用户选定一条已有参考歌曲。
2. 用户上传或通过浏览器录制自己的演唱。
3. 系统执行本地对齐与 DSP 评分，展示音准、节奏、完整度和稳定性。
4. 结果归入当前账号，可回看、删除，并可选择公开到娱乐排行榜。

### 4.5 链接导入

1. 用户可以粘贴直接音频 URL；受支持音乐/视频网站 URL 仍属于后续阶段。
2. 服务端进行 URL 标准化、SSRF 防护、DNS 地址固定和逐次重定向检查。
3. 对公网直接音频执行类型、大小、下载时间、时长、格式和重定向限制后进入
   现有上传流程。
4. 对平台页面只读取允许的元数据或官方 API 信息；Tavily 可辅助发现和元数据检索，
   不能作为绕过平台下载限制、版权或 DRM 的手段。
5. 无权处理的链接必须拒绝，并解释可行替代方式，例如由用户上传其有权使用的文件。

## 5. 功能需求

### 5.1 分析与证据

- **FR-AN-001（必须，✅）** 支持受限大小和时长的音频上传，并在解码前后执行校验。
- **FR-AN-002（必须，✅）** 持续展示任务进度、当前阶段、警告和最终状态。
- **FR-AN-003（必须，✅）** 输出 BPM、调性、能量、节拍/起音等本地 DSP 结果。
- **FR-AN-004（必须，✅）** 在 Provider 可用时输出带时间的歌词、声源、声音事件和
  情绪线索，并保留模型来源。
- **FR-AN-005（必须，✅）** 对歌词密度、重复、重叠、越界和验证器结论做质量检查；
  不能确认可靠歌词时保守留空并提示。
- **FR-AN-006（必须，✅）** 区分 BPM 的半拍/双拍歧义，不把模型猜测覆盖为 DSP 事实。
- **FR-AN-007（必须，✅）** 允许用户校对歌词、查看旧版本和定向重听局部。
- **FR-AN-008（应该，🟡）** 针对每种 Provider 建立固定真实样例兼容测试，并记录
  首包时间、总耗时、超时、忙碌和结构化输出成功率。

### 5.2 教学式导赏

- **FR-GD-001（必须，✅）** 分析完成后，从已保存证据自动生成可用的基础导赏，
  不以再次调用模型作为进入教学界面的前置条件。
- **FR-GD-002（必须，✅）** 导赏包含一句话核心表达、整体意境、情绪发展弧线、
  段落作用、时间地图和关键复听时刻。
- **FR-GD-003（必须，✅）** 每个重要时间段包含听觉事实、开放解释、表达作用、
  音频证据、附近歌词、复听任务、其他可能理解和置信度。
- **FR-GD-004（必须，✅）** 内容表达优先遵循：
  “感受到什么 → 听到了什么 → 为什么形成这种感受 → 它在表达什么 → 怎样复听”。
- **FR-GD-005（必须，✅）** 避免术语堆砌；使用乐理术语时立即说明用户能听见什么。
- **FR-GD-006（必须，✅）** 证据不足时允许没有情绪弧线或少于三个关键时刻，
  不为了满足数量制造内容。
- **FR-GD-007（应该，✅）** 用户可在基础导赏上请求当前 Provider 做模型增强；
  增强期间原地图和问答继续可用。
- **FR-GD-008（必须，✅）** 歌词或分析证据变化后旧地图标记为过期，并允许按最新
  证据重建。

### 5.3 边听边问

- **FR-CH-001（必须，✅）** 支持当前播放位置、当前 15 秒、波形选区和 A/B 两段提问。
- **FR-CH-002（必须，✅）** 支持询问乐器、歌词、旋律、和声、节奏、音色、力度、
  配器、空间感、情绪和段落变化。
- **FR-CH-003（必须，✅）** 自动关联歌曲 ID、当前时间、选择范围、当前段落、附近
  歌词、附近分析证据、先前对话和用户音乐基础。
- **FR-CH-004（必须，✅）** 回答首先直接回应用户的问题或感受，然后给出可点击的
  精确时间、听觉依据、表达作用、复听任务和其他可能理解。
- **FR-CH-005（必须，✅）** 回答明确区分“可观察事实”“基于事实的音乐解释”
  和“主观/文化性的可能理解”。
- **FR-CH-006（必须，✅）** 不把意境当作唯一标准答案，不在无证据时推测创作意图。
- **FR-CH-007（必须，✅）** 默认检索附近事件，证据不足时最多局部重听两个片段，
  单段不超过 30 秒；普通问答不得重跑整首歌曲。
- **FR-CH-008（必须，✅）** Provider 不支持局部音频或重听失败时，使用已保存证据
  回答并显示降级状态。
- **FR-CH-009（应该，✅）** 回答提供推荐追问和需用户确认后执行的播放器动作。
- **FR-CH-010（应该，⏭）** 允许用户把自己的理解标记为“已听出”“仍不确定”，
  并将反馈用于后续教学，而不是自动判定对错。

### 5.4 播放器

- **FR-PL-001（必须，✅）** 所有报告、歌词、地图和问答共享一个播放时钟。
- **FR-PL-002（必须，✅）** 点击时间范围可以跳转或播放相应片段。
- **FR-PL-003（必须，✅）** 支持波形框选、选区循环、A/B 范围和连续 A→B 播放。
- **FR-PL-004（必须，✅）** 显示段落标记和同步歌词。
- **FR-PL-005（必须，✅）** 模型只能返回白名单播放器动作，且动作必须由用户点击
  后执行，不能让模型自动控制播放。
- **FR-PL-006（应该，⏭）** 支持人声、鼓、低音和其他乐器的独听或静音，并明确
  标注分离伪影。

### 5.5 账号、历史与对话

- **FR-HI-001（必须，✅）** 分析、对话、音频和演唱记录按账号隔离。
- **FR-HI-002（必须，✅）** 每首歌曲允许建立多个独立对话，支持切换和删除。
- **FR-HI-003（必须，✅）** 历史支持打开、重命名、删除、歌词修订和结果对比。
- **FR-HI-004（必须，✅）** 保存歌曲级对话记忆、分析时的 Provider 和用户选择的
  音乐基础。
- **FR-HI-005（应该，✅）** 保存用户主动确认已经听出的音乐概念；没有用户确认时
  不把一次回答等同于“已经学会”。

### 5.6 演唱评分与排行

- **FR-SG-001（必须，✅）** 允许以已有歌曲为参考，上传或录制个人演唱。
- **FR-SG-002（必须，✅）** 返回音准、节奏、完整度、稳定性、对齐误差和综合分。
- **FR-SG-003（必须，✅）** 保存个人记录并支持删除；排行榜只对已登录用户开放，
  且用户显式加入后每个账号才展示娱乐分类最高分。
- **FR-SG-004（必须，✅）** 明确评分是练习反馈，不是专业声乐等级、健康或医学结论。
- **FR-SG-005（应该，✅）** 提供带参考/演唱时间的音高偏差地图，以及最多三个
  有证据支持的优先练习时间段和练习任务。
- **FR-SG-006（应该，🟡）** 排行榜默认不公开，用户可以显式加入或退出，只返回
  排行所需字段；匿名昵称模式仍待实现。

### 5.7 Provider 与模型配置

- **FR-PV-001（必须，✅）** 用户可从右上角选择预设、受允许的自定义私有地址或
  受控目录下的本地模型。
- **FR-PV-002（必须，✅）** 分析保存实际 Provider 配置；导赏、重听和问答恢复该
  配置，不接受浏览器临时注入任意 URL。
- **FR-PV-003（必须，✅）** 接入层按能力描述音频输入、结构化输出、流式事件、
  局部重听和限制，不以端口号或模型名称作为协议。
- **FR-PV-004（必须，✅）** Provider 探测与真实推理分开；“服务在线”不能被显示为
  “音频分析可用”。
- **FR-PV-005（应该，🟡）** 形成 Provider 注册表、标准错误、重试/退避策略和统一
  契约测试，使更多主流音频多模态模型可通过独立适配器接入。
- **FR-PV-006（必须，✅）** 对 Worker busy、首包超时、结构错误和不支持音频分别
  报告，不把 20 多个相同分块错误堆成不可读提示。

### 5.8 运维与分布式执行

- **FR-OP-001（必须，✅）** `8000` 根页面作为 Debug Console，显示任务状态、
  阶段耗时、问题、Provider 信息和可展开详情。
- **FR-OP-002（必须，✅）** 支持取消、断线重连、终态轮询和失败后的资源清理。
- **FR-OP-003（应该，✅）** Redis 保存跨进程任务状态，Celery Worker 可跨机器执行
  分析，并使用原子全局容量限制。
- **FR-OP-004（应该，✅）** Redis 模式下，导赏增强、问答等直接工作使用带心跳
  和崩溃过期回收的全局租约，多个 API 进程不能绕过总量和用户上限。
- **FR-OP-005（必须，✅）** 局域网部署必须明确配置监听地址、Web Origin、反向代理
  和模型服务可达性；前端不得硬编码 `127.0.0.1` 作为远端用户的 API 地址。

### 5.9 链接导入

- **FR-LK-001（必须，✅）** 支持直接返回音频的公网 HTTP(S) URL，并把下载结果
  送入现有的用户隔离上传、解码、分析和历史流程。
- **FR-LK-002（必须，✅）** 禁止 URL 凭据、fragment、本机、私网、链路本地和
  非公网地址；域名的全部 DNS 结果必须为公网地址。
- **FR-LK-003（必须，✅）** 网络连接固定到已经验证的公网 IP，同时保留原始域名
  的 Host、SNI 和证书校验，避免验证后 DNS rebinding。
- **FR-LK-004（必须，✅）** 每次重定向重新检查 URL，限制重定向次数、下载时间、
  Content-Type、声明/实际字节数和解码后的音频时长。
- **FR-LK-005（必须，✅）** 当前不解析 YouTube 等视频网页，也不绕过登录、付费、
  地域、版权或 DRM；界面必须明确这一边界。
- **FR-LK-006（应该，⏭）** 视频平台只通过其官方 API 和明确授权接入；Tavily
  只能辅助发现或补充元数据，不能充当媒体下载器。

## 6. 结构化数据契约

### 6.1 音乐理解地图

导赏不是一段不可操作的 Markdown。`MusicUnderstandingMap` 至少保存版本、
歌曲/分析版本、总览、情绪弧线、段落、关键时刻、证据引用和时间事件。

每个时间事件至少包含：

```text
start_s
end_s
section
observation
interpretation
expressive_role
audio_evidence
lyrics_context
listening_task
alternative_readings
confidence
```

约束：

- `start_s` 和 `end_s` 必须落在歌曲时长内且 `start_s < end_s`；
- 音频证据必须来自已保存证据或本次受限局部重听；
- 解释不得伪装成观测事实；
- 置信度表示当前证据支持程度，不表示审美判断的正确率；
- 保存证据版本，基础结果变化后可判断地图是否过期。

### 6.2 教学问答

请求上下文由服务端组装，至少包含歌曲、播放位置、选区或比较范围、附近段落、
附近歌词、附近证据、对话历史、用户听觉水平和重听策略。

回答返回结构化数据：

```text
answer
time_ranges
evidence
listening_task
suggested_questions
player_actions
alternative_readings
confidence
relistened
insufficient_evidence
```

其中 `time_ranges` 必须可点击，`evidence` 必须引用本次范围或本地证据，
`player_actions` 只能引用本次返回的合法范围。

### 6.3 证据类型

- **观察事实**：时间、响度/能量、节拍、起音、频谱特征、已验证歌词或模型明确
  听到的声源事件。
- **音乐解释**：由一项或多项事实支持的情绪、张力、段落作用和叙事关系。
- **可能理解**：依赖听者经历、语境或文化联想的开放阅读。

三者必须在存储、提示词和界面上保持可辨识。

## 7. 非功能需求

### 7.1 可靠性与降级

| 故障 | 必须保留的体验 |
| --- | --- |
| 统一模型不可用 | DSP、任务报告和基于现有证据的基础导赏 |
| 歌词不能确认 | 保守空歌词、质量提示、人工校对入口 |
| 模型增强失败 | 原基础地图继续可用，显示可读错误 |
| 局部重听不支持或失败 | 使用已保存证据回答并标记未重听 |
| 波形生成失败 | 音频仍可播放，并可用数值时间选择 |
| Redis 不可用且配置允许 | 单进程开发模式可使用内存任务后端 |

错误必须聚合相同原因，保留可展开细节，不能用几十条重复警告淹没用户。

### 7.2 性能

- 基础导赏从缓存分析生成时不得依赖模型网络往返；
- 前端使用 SSE 展示长任务进度，并以轮询作为断线兜底；
- 问答只检索附近证据，局部音频总量必须有硬限制；
- 波形、标准化音频和可复用派生结果应缓存并安全回收；
- 对 Provider 记录排队、首包、推理和总耗时，区分“慢”与“失败”。

### 7.3 隐私与安全

- 上传、音频流、历史、任务、调试信息和评分均在后端按用户授权；
- Cookie、密码、路径、URL、重定向、上传大小和解码时长遵循现有安全边界；
- 自定义模型地址只允许明确的私有网络范围或管理员许可范围；
- 选择网络 Provider 前后都应说明哪些数据会离开本机；
- 链接导入必须防止 SSRF、DNS rebinding、私网探测、无限重定向和超大下载；
- 不实现版权规避、DRM 绕过或违反来源平台条款的下载。

### 7.4 可维护性

- Pydantic/TypeScript 结构化契约保持一致，并对破坏性变更升级 Schema 版本；
- 路由只负责鉴权和 HTTP 协议，业务编排、Provider、持久化和领域模型分层；
- 外部模型使用适配器和能力协议，不在 UI 或业务服务中散落方言判断；
- 新功能至少覆盖成功、权限、输入边界、失败降级和幂等/并发路径；
- README 说明当前运行方式，本文档维护产品范围，部署细节维护在独立部署文档。

### 7.5 可用性与无障碍

- “边听边问”是核心区域，应拥有完整横向空间和清晰的当前上下文提示；
- 所有波形操作都要有表单或键盘可达的等价方式；
- 颜色不能成为置信度、选区或状态的唯一表达；
- 时间、播放状态、错误和异步更新应使用可访问标签与适当 live region。

## 8. 验收标准

### 8.1 一首歌的完整导赏

- 分析完成后无需再次点击模型按钮即可进入可用教学区；
- 页面同时显示核心表达、整体意境、段落/时间地图、复听任务和证据支持度；
- 点击任一合法时间范围会控制同一个播放器；
- 证据稀疏时页面明确说明，不生成没有依据的歌词、情绪或关键时刻；
- 可选模型增强失败、等待或超时不阻止基础地图和问答。

### 8.2 一次教学问答

- 请求关联正确歌曲和对话，不能访问其他账号数据；
- 当前 15 秒、手动选区和 A/B 三种范围都能形成合法上下文；
- 回答至少有一个可点击时间范围、听觉依据和可执行复听任务；
- 事实、解释和可能理解可区分；
- 无证据时明确说不知道或证据不足，不猜测创作意图；
- 相同 `client_request_id` 不会产生重复消息或重复推理发布。

### 8.3 Provider 接入

一个新 Provider 只有在以下项目通过后才可标记为“支持”：

1. 能力探测能区分在线、文本可用和音频可用；
2. 短中文、短英文、含人声多乐器和较长音频样例完成协议测试；
3. 输出经过统一 Schema 校验和证据时间校验；
4. 超时、忙碌、取消、无音频能力和无效 JSON 均映射为标准错误；
5. 分块并发不超过服务声明能力，重试使用退避且不会形成请求风暴；
6. 分析、导赏增强、局部重听和问答能力分别标明支持情况。

### 8.4 完成定义

每个需求只有在以下条件同时满足时才能标记为完成：

- 用户路径可在正式 React 界面完成；
- API 和前端类型契约一致；
- 正常路径和主要失败路径有自动化测试；
- 权限、资源上限、取消和清理已检查；
- Debug Console 或用户界面提供可操作的失败信息；
- README、本文档和相关部署文档没有互相矛盾；
- 不依赖未提交的本地样本、模型权重或固定局域网端口才能运行基础降级链路。

## 9. 路线图

### 阶段 A：教学体验收尾（当前）

- ✅ 教学式总览与结构化音乐理解地图；
- ✅ 自动证据版导赏与可选模型增强；
- ✅ 点击时间跳转、当前位置问答和复听任务；
- ✅ 歌曲级多对话保存；
- ✅ 波形框选、A/B 循环与比较；
- ✅ 同步歌词和推荐追问；
- ✅ 用户主动确认的听觉概念进度；
- 🟡 用真实 Provider 兼容矩阵持续验证 8004/8005 等现有服务；
- 🟡 补齐性能基线、无障碍检查和端到端浏览器测试。

### 阶段 B：输入和模型生态

- 建立可扩展 Provider 注册表与契约测试包；
- 按协议逐步接入更多主流音频多模态服务；
- ✅ 导赏与问答等 API 直接工作使用 Redis 跨进程全局租约；
- ✅ 安全、合规的公网直接音频链接导入；
- 评估需要排队/断线续跑时是否把教学推理迁移为后台任务；
- 评估通过官方 API 支持视频平台链接，Tavily 仅用于发现与元数据补充；
- 为中文和英文建立固定回归集，再决定日语支持优先级。

### 阶段 C：个人听觉训练

- 分轨独听和静音；
- 根据用户音乐基础动态调整解释深度；
- ✅ 由用户确认“已听出”的音乐概念；
- 把复听任务组织成连续的个人训练课程；
- ✅ 为演唱结果增加带时间的偏差地图和练习建议。

### 阶段 D：生产化

- 生产级身份系统、密钥管理、审计、备份和数据库；
- API、教学推理、文件存储和 Worker 的完整横向扩展；
- 配额、速率限制、可观测性、恢复演练和跨节点缓存生命周期；
- 在明确隐私政策和内容授权机制后再评估公网多租户服务。

## 10. 非目标

- 🚫 给出唯一、权威的音乐意义或审美结论；
- 🚫 在没有资料或声音证据时断言创作者真实意图；
- 🚫 把模型生成的歌词当作版权歌词库；
- 🚫 绕过音乐/视频网站的登录、付费、地域、版权或 DRM 限制；
- 🚫 把娱乐性演唱评分包装成专业考试、声带健康或医学诊断；
- 🚫 在当前本地认证和 SQLite 架构上直接承诺不受信任的公网多租户部署；
- 🚫 为了显示完整报告而制造置信度、歌词、段落或情绪。

## 11. 产品指标

以下指标用于发现问题，不用于鼓励模型输出更多未经证实的内容：

- 分析成功率，以及“完整模型结果 / 明确降级结果”的比例；
- 基础导赏可用率和模型增强成功率；
- 带有效时间证据的回答比例；
- 点击时间范围后正确跳转/循环的成功率；
- Provider 排队、首包、推理和端到端延迟；
- 歌词被人工修订、定向重听或判为不可靠的比例；
- 相同失败原因被正确聚合的比例；
- 用户完成复听任务、继续追问或主动确认“已听出”的比例（仅在本地、获得同意
  且不上传私人内容的前提下统计）。

## 12. 待决策问题

1. 链接导入首批只支持直接音频 URL，还是同时接入一个有明确官方 API 的视频平台？
2. Provider 应按“实验 / 兼容 / 验证”三级展示，还是只展示逐项能力？
3. 模型增强应继续由用户主动触发，还是在空闲且已授权时自动排队？
4. 排行榜以同一首参考歌曲分榜为主，还是允许跨歌曲娱乐总榜？
5. 概念掌握由用户显式确认、复听任务完成情况或小测验中的哪些信号组成？
6. 日语支持应在 Provider 回归集稳定后进入阶段 B，还是继续放到更晚阶段？

这些问题在作出产品决定前保持开放，不应由某个 Provider 的临时能力反向决定
长期产品结构。
