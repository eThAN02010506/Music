# 教学推理后台化评估

对应 PRD 阶段 B「评估需要排队/断线续跑时是否把教学推理迁移为后台任务」。这是
一次决策记录，不是已实施的改造。

## 现状（2026-08）

教学 HTTP 请求（导赏增强、问答、局部重听）由接收它的 API 进程**同步完成**：

- `api/routers/teaching.py:280` 在 `direct_work_limiter.lease` 内直接
  `await service.answer_music_question(...)`；
- 模型推理耗时（5–15 秒，视端点）占住该 HTTP 连接，浏览器等待响应；
- `direct_work_limiter` 限制每用户 1 个、全局最多 `MAX_DIRECT_WORK`（默认 2）个
  直接工作；教学请求未被投递为 Celery 后台任务；
- 教学领域有自己的异步状态：消息预留 `pending → complete/failed`，服务重启用
  `recover_pending` 结算遗留。

## 什么时候值得迁移到后台任务

当前同步模型在以下前提下是合理的：

| 前提 | 现状 |
| --- | --- |
| 单用户/低并发本地或局域网 | 成立；用户自己等待几秒可接受 |
| 模型端点相对快（5–15 秒） | 成立；80% 问答在 15 秒内返回 |
| 浏览器可接受长请求 + 等待 | 成立；前端有发送中状态 |

触发迁移的信号（出现其一才做）：

1. **多用户公网部署**：请求占住 API worker，5 秒问答 × 100 用户 = 500 秒占用量，
   worker 池被耗尽；
2. **模型端点变慢**（如 Comni 30+ 秒首包）：同步等待体验差，需要「提交后轮询/SSE」；
3. **需要断线续跑**：用户在请求中断后仍希望得到答案（消息已预留为 pending，
   后台完成后可取回）；
4. **需要跨节点排队**：教学与整曲分析共享模型端点门，需要统一排队语义。

## 迁移会动什么

- 路由改为「提交 → 立即返回 pending 消息」；
- 需要一个队列（复用 Redis/Celery 的 `task_queue` 或新增教学队列）；
- 后台完成回调复用现有 `complete_message`/`fail_message`（幂等预留已支持）；
- 前端从「等待响应」改为「轮询/SSE 消息状态」。

好消息：**领域层已为迁移做好准备**——消息预留/完成/失败、`recover_pending`
结算、`client_request_id` 幂等都已存在，迁移主要是路由层 + 队列接线，不改领域模型。

## 结论

**当前阶段不迁移**。本地/局域网单用户下同步模型体验可接受，且教学领域已具备
后台化的持久化地基。当出现上述任一信号（尤其多用户或端点显著变慢）时，按本
文档的改动清单迁移，成本主要是路由层改造。
